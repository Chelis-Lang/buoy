# Golden regeneration and mutation policy

Status: release-gate policy for active schema v3.

## Frozen goldens

Canonical bytes, full digests, normalized diagnostics, generated Aeneas output, fixture polarities, migration dispositions, and proof bindings are reviewed artifacts. They are never rewritten merely because an implementation emits a different value.

Active v3 goldens include:

- canonical, construction, state, policy, disposition, and impact artifacts under `fixtures/hardening/v3/`;
- registered digest vectors under `fixtures/digest/v3/`;
- binding diagnostic goldens under `fixtures/content-addressed-bindings/v1/goldens/`;
- logical mount and artifact goldens under `fixtures/logical-mount-artifact-bindings/v1/goldens/`;
- the atom-revision golden in `tests/core_contract.rs`;
- exact proof and negative-control bindings in `tests/proof_bindings.rs` and `proofs/core/*.toml`; and
- normalized `proofs/spikes/aeneas/generated/Integrity.lean` output.

The v1 and v2 schema directories and hardening fixtures remain historical data. Active readers do not accept or relabel their identities.

### Publication CLI fixture

Publication CLI tests build one BLAKE3-only binary in `target/publication-cli-blake3-fixture`.
The four behavior checks use that image, not the shared Cargo product binary.
The checks cover report, evidence, page, and external-link bytes.
Package identity uses typed contracts and the explicit three-variant package checks, not a golden for incidental build features.

### Chelis consumer contracts

Run the focused saved-input contracts for each collision-resistant member:

```sh
for member in blake3-256 sha-256
do
  cargo test --locked --offline -p chelis-provenance \
    --no-default-features --features "$member" \
    --test adapter_contract --test integration --test bind_conversion \
    --test binding_regeneration --test rebind_regeneration
done
```

Check the general contracts in the all-feature image:

```sh
cargo test --locked --offline -p chelis-provenance --all-features \
  --test adapter_contract --test integration --test bind_conversion \
  --test binding_regeneration --test rebind_regeneration
```

The compact-binding suites use their existing collision-resistant feature guards.
The all-feature image does not execute those suites.

Selective repair changes only fields with known current values.
Malformed or absent fields stay unchanged while other records receive valid repairs.
Unresolved references retain their saved commitments.
An unreadable compact object or absent authority produces no invented successor object.

A runner can refer to the source file that contains its own digest field.
The write changes that file's digest, so the next plan remains nonempty.
Rebind reports divergence instead of a false convergence result.
The contracts check the saved write and the next bound/current digest pair.

A separate library-consumer smoke can exercise public APIs without CLI callers.
Temporary API smoke does not by itself provide persistent full-lane coverage.

## Regeneration protocol

A golden changes only when one reviewed change:

1. identifies the governing schema/domain and authoritative preimage;
2. updates the schema decision before expected output;
3. preserves the immutable historical source data;
4. updates positive, negative, permutation, collision-observation, and mutation cases together;
5. independently reproduces the new value and shows obsolete/mixed values fail;
6. updates every affected carrier, derivation, proof, freshness binding, report, and impact disposition; and
7. runs the read-only acceptance gate after explicit maintainer regeneration.

Maintainer generators expose explicit `--write` or output-redirection workflows. Binding goldens use `BUOY_WRITE_BINDING_GOLDENS=1` only during reviewed regeneration.

The Aeneas derivation uses `BUOY_WRITE_AENEAS_GOLDEN=1` only during reviewed regeneration. Acceptance does not set this variable.

The acceptance gate does not set write controls. It compares generated bytes with committed files.

There is no snapshot-accept, dual-read, or algorithm-fallback mode.

## Mutation and negative-control claim

Mutation tripwires cover selected lifecycle, surface, freshness, binding, canonical-boundary, policy, impact, no-laundering, aggregation, XXH3 profile, migration, and external-boundary faults. Formal lanes include intentionally false proof controls. Each proves only that its named assertion rejects that named fault. It does not show that all mutants are killed, annotations are complete, parsers are correct, digest equality is collision-resistant, or the verified representation corresponds to prose, rustc, LLVM, or native code.

## Generated and derived artifacts

Intentional generated or mirrored output requires exact source/target/tool/configuration bindings and a consistency oracle. Byte equality establishes only the declared derivation relation. It is not independent evidence and does not establish behavioral correctness, semantic correspondence, or cryptographic integrity.

## Production-readiness regeneration enforcement

Before a reviewed golden change is accepted:

1. `devenv tasks run buoy:fixtures` must behaviorally execute each closed operation and ordered mutation; vocabulary or manifest shape alone is insufficient.
2. `devenv tasks run buoy:reference`, `buoy:schema`, and `buoy:core` must retain strict decode/re-encode bytes, malformed rejection, complete parity, graph-derived governance, and dependency-independent authority checks.
3. `devenv tasks run buoy:coverage` must include every generator/checker changed by regeneration and retain exact line/region/function/branch equality without rounding or broad exclusion.
4. `devenv tasks run buoy:adversarial` must replay committed fuzz corpora, named mutation tripwires, faults, local tools, and current campaign bindings.
5. Run full fuzz and mutation campaigns locally through their pinned focused commands.
6. `devenv tasks run buoy:obligations` must refresh each affected ledger row, proof binding, dependency impact, and explicit blocker.

Run the mutation campaign with `devenv tasks run buoy:mutation-campaign`.
Run the fuzz campaign with `devenv tasks run buoy:fuzz-campaign`.
Both independent tasks execute their declared campaigns without shell-startup acceptance tasks.
A selected mutant must compile before its test result can count as caught.

A parser, Unicode, report, verifier, campaign tool, dependency, or wrapper update also refreshes its exact source bindings. Acceptance checks never write goldens implicitly.

License metadata can also change exact campaign configuration bindings.
Run the real campaign before a new record replaces stale evidence.
The repository checks records against their saved generation dates.
Negative date controls use fixed fixture dates.
Canonical acceptance still checks campaign expiry at its declared date.
The ledger uses the reviewed campaign observation date, `2026-10-30`.
Future-generation and expiry checks still apply at that date.

The adversarial CLI self-test also uses fixed copied fixture dates. It does not alter real campaign dates or bindings.

## Nested command isolation

Focused-command controls use one mutex for each Cargo build and its complete test process.
Cargo shares CLI output paths across feature variants.
Parallel oracle workers must not replace another worker's executable before that worker exits.
The controls still test full-feature and reduced-feature commands.

The mutation campaign omits debug symbols from its build artifacts.
The campaign disables incremental builds and ambient compiler wrappers.
It keeps debug assertions and all selected behavioral controls.
